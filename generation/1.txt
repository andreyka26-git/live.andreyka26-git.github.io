## Key takeaways / Advices

Now let me share what I have learnt during these years, and what I have done differently.


### Run in your mind

If you are preparing for an interview specifically - this is the most important advice for you.

This should be your plan for specific problem:



1. Before starting writing code - have a fully compiled mental model about your solution, you should “see” your array/graph or hashmap, and what will be happening to it and how the solution will return the correct answer.
2. Only after having a very specific mental model of solution - you just implement it as following a specific plan.
3. Before clicking “Run” or “Submit” you should debug line by line your code on the example input and be 100% confident it will work. This is probably one of the most important skills to be able to do it fast.
4. When you click Run and Submit you 100% should pass the first 3 given examples that you have debugged in your mind + preferably all test cases along with edge cases that you have anticipated and run against in your mind as well.

Just writing code as you go, aka “play around” with the code - is very counterproductive and you learn nothing by doing that at all.

Keep in mind - drawing while thinking about a solution and when you are debugging is good - but typically you won’t have access to drawing. It is better to learn drawing and debugging via comments in the code.


### Up to 2 hours per problem

Beware that it means 2 hours for thinking about a potential solution, maybe trying it out. If you are stuck after 2 hours - check the solution. Everything after that is counterproductive. Typically, with 70-80% confidence the solution that you would see - is never the solution you can come up on your own. \
 \
The flow:



* read problem and examples
* focus on how you can solve input from “examples”
* after 20-30 mins if you are stuck - start reading hints. one after 10-20 mins
* if you don’t have any idea about the solution - just go to the solution tab

Note though - usually the “solution” tab by Leetcode is much harder to understand than solutions posted by people.

Sometimes Neetcode posts good solutions on Youtube.


### How to learn new pattern

In general, the majority of the problems have some specific pattern. Usually it is not something that you can come up on your own (at least come up fast). Initially you don’t know any of the patterns.

Specifically for that reason, you take ONLY SINGLE pattern a day. Don’t solve problems involving 5 different patterns the same day, as it is harder to memoize and learn them.

Keep notes with the patterns and code snippets along with the canonical problem for that pattern. Believe me you will thank me later. I can recall everything in 30-60 minutes before the interview now.


![alt_text](images/image6.png "image_tooltip")


There are simple patterns that you must know at some point: sliding window, DP, dijkstra, union find, 2 pointers, binary search, etc.

There are some advanced ones that you usually don’t want to focus on, as they are rarely asked: segment tree, fenwick tree, binary lifting, kmp, etc.


### You don’t need premium

Maybe you do, but I personally never used premium at all.

If you want to solve specific problems for a specific company you are preparing for -> ask somebody with a premium to send a screen, however for me it worked 0 times, I never had any problems on real interview from there.

If some problems are “locked” - try find it here: [https://www.lintcode.com/](https://www.lintcode.com/)

Lintcode has some “leaked” problems as far as I know, never used it myself though.


### Do only lists

As I've been solving Daily leetcode for one year already - I can say that 60-70% of all the problems there are bad problems that don’t have a specific pattern to learn/recall. Some of them are very hard problems that you will never be asked on the real interview unless you are interviewing for hedge funds.

Same I can say about doing random questions - very high chane that you’ll get a bad problem.

Before some years - every leetcode problem had a likes/dislike ratio - it was a very good indicator before, but not anymore, as they did the same thing as Youtube did.

Now you should focus on lists only, you have 3 that I mentioned. By solving all 3 of them you’ll have 200-300 solved problems, which is enough for an average FAANG big tech interview.


### Can I solve any problem after 750 solved ones?

After all this Leetcode experience I have the following confidence / probability of being able to solve given random (potentially bad) problem:



* easy - 99% I will solve it
* mid - 50-60% I will solve it
* hard - 20-30% I will solve it

However for good problem from the list it looks like that:



* easy - 100% I will solve it
* mid - 70-90% I will solve it
* hard - 50-60% I will solve it

Interesting takeaway - you cannot do better than your genetics allow you. It is about general cleverness / IQ (fluid intelligence) and is capped by your genes and brain. You can do nothing about it.

I’m in general not that clever a person (coming up with solutions to unknown problems) - therefore I upscaled my potential via discipline and crystalized intelligence. But now I’m 100% sure I cannot be top 1-2% of these algorithms competitions, and I cannot pass hedge funds for sure with my algos skill.

But, the average engineer is definitely able to get the level to one that will allow them to pass up to senior positions in big tech, this is for sure true.
